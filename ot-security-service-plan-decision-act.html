01 / Executive brief

Start with one site. Build a service that defenders can trust.

Launch a repeatable managed security service for OT by applying Plan → Decision → Act to every customer, site and detection wave. Begin with service assurance and access/boundary coverage, then expand according to operational consequence and evidence readiness.

Planning assumption: detection use cases are treated as validated for this plan, as requested. Customer-specific applicability, telemetry availability, configuration and authorization still need deployment decisions. This document does not change the validation status stored in the source catalog.

DECISION

ACT

What makes a good first customer?

Choose a site with a committed operational owner, stable access architecture, usable logs and a clear business consequence. Prefer a manageable scope over immediate fleet deployment. The first site establishes the reusable onboarding method; later sites still require their own policy and readiness review.

1. Data sources

Inventory the systems that can observe the behavior. Record the customer, site, zone, asset owner and collection limits for each source.

OT systems
Programmable logic controllers, remote terminal units, supervisory control, operator interfaces and distributed control systems can provide native status, command outcomes and alarms. Check which events the device actually exports.
OT network
Passive sensors such as Nozomi, Claroty, Zeek or Suricata can provide flows or decoded operations where supported. Record the monitored segment, decoder support and visibility limits for encrypted or proprietary traffic.
Infrastructure
Firewalls supply route and allow/deny evidence. Virtual private network and remote access systems provide session records. Endpoint detection and response supplies host activity where the agent and configuration are supported.
Engineering
Engineering and operator workstations, programming tools and project repositories can show who initiated work, what project was involved and what version was approved. Use device audit or a trusted project comparison to confirm the resulting state.

2. OT data and events

Define which event answers each question. Keep the observed action, its result and any independently confirmed process effect as separate fields or observations.

Access
Capture identity where available, source, destination, session ID, authentication result and the approved access scope. Link remote gateway access to the destination session before attributing later activity.
Configuration
Capture the target device, operation, project or object, native outcome and approved change record. Keep before and after values or versions when the source provides them.
Network traffic
Collect the initiator, responder, protocol and decoded operation for Modbus, DNP3, IEC 104, OPC UA or other installed protocols. A flow can show connectivity. A decoded request and response are needed for operation and outcome claims.
System logs
Use operating system, service and application audit to observe logons, process execution, service changes and log clearing. Preserve provider and original event identifiers for investigation.
Process events
Collect alarms, state, setpoints, mode, source time and quality indicators. Compare them with the expected operating mode and independent observations where available. A stale reading can indicate loss of view while the physical process continues.

3. Collection and ingestion

Choose supported collection paths through approved security boundaries. Track source freshness, parsing and time quality with OT-DC-071 and OT-DC-072.

Collectors
Use supported syslog, application programming interfaces or approved agents. Confirm expected events, field completeness and production constraints before onboarding.
Forwarders
Route records to the approved destination and attach customer, site and source identifiers. Preserve the native event and original timestamp alongside any enrichment.
Queue and buffer
Buffer events where appropriate for connection outages or bursts. Monitor backlog, drops, retries and duplicates. Test recovery so delayed data can be distinguished from current activity.
Transport
Use authorized routes and authenticated, encrypted transport where supported. Verify delivery and retain event and ingest times so analysts can account for delay.

4. OT SIEM

The security information and event management platform turns collected observations into searchable evidence and detection results.

Parsing
Extract source fields while retaining the original record or its reference. Treat parser failures as coverage gaps and retain the event for review.
Normalization
Map records to a common schema for customer, site, asset, identity, session, operation, outcome and time. Preserve vendor-specific details and represent missing values explicitly.
Correlation
Use customer and site scope, stable asset or session identifiers and time uncertainty to relate records. OT-DC-070 connects suspicious activity across IT, the industrial demilitarized zone and OT where the evidence supports the relationship.
Detection
Apply the catalog predicate with site policy, asset roles, approved paths and maintenance context. Record the supporting events, the matched condition and evidence gaps in the alert.

5. SOC

The security operations center turns the alert and its evidence into a documented decision for the responsible owner.

Monitoring
Watch alerts and telemetry health together. Identify which detections are affected when a source stops reporting or a parser fails.
Triage
Check asset criticality, native outcome, approved activity and immediate operational concerns. Assign urgency and confidence separately and record the next evidence needed.
Investigation
Reconstruct the event sequence across access, engineering and process sources. Compare plausible maintenance or fault explanations and separate what happened from what remains a hypothesis.
Response
Route evidence and proposed action to the agreed customer owner. Customer operations directs process-affecting decisions. Use OT-DC-074 to track escalation or evidence delivery failures. SOC incident response and forensics.

Team walkthrough using OT-DC-032

  1. Source. An engineering workstation, controller or passive sensor observes a programming operation.
  2. Event. Record the source, target, operation, project, timestamp and native result where available.
  3. Collection. Preserve the original record, customer and site identifiers, and clock context through forwarding.
  4. Detection. Compare the operation with the approved engineering host, change scope and window. Link device audit or a trusted project comparison where available.
  5. SOC decision. Explain whether the evidence shows a request, an accepted operation, a confirmed logic change or a supported process effect. Check authorized maintenance and hand off unresolved operational questions to the control owner.

Staffing and coverage

These are required functions, not fixed full-time headcounts. Size the service using contracted hours, customer/site count, measured alert volume, investigation effort, leave cover and specialist escalation. Confirm an available customer operational contact whenever the SOC is expected to escalate.

Automation boundary

Automate approved enrichment, evidence preservation, deduplication and ticket routing. Controller isolation, operating-mode changes, operational-account disruption and process/safety actions require the customer’s agreed decision process and authorized personnel.

07 / Operating the service

From a signal to an explained incident

  1. Receive and qualify. Confirm customer/site, source health, event time and whether the signal reports a request, accepted action or independent effect.
  2. Enrich. Add asset role, process area, criticality, approved path, identity/session, maintenance and change context.
  3. Investigate. Follow attributable sessions and native actions. Separate observation from hypothesis, and check normal operational alternatives.
  4. Decide and escalate. Assign consequence and confidence separately. Notify the agreed customer owner with evidence and a recommended next action.
  5. Track action and hand over. Record customer decisions, acknowledgments, containment/recovery ownership and unresolved observations.
  6. Improve. Update policy, exceptions, runbooks or content through change control and retain traceability.

Required incident narrative

QuestionWhat the analyst provides
What happened?A time-bounded sequence of supported observations with source-event references.
How did it happen?Linked identities, access paths, sessions and actions where the evidence supports those connections.
What was affected?Assets, process areas and dependencies; distinguish potential consequence from an observed physical effect.
How confident are we?Supporting evidence, missing observations, time uncertainty and alternative operational explanations.
What happens next?Specific evidence to collect, recommended action, responsible owner and escalation urgency.
Example, not an observed incident: an out-of-scope remote session (001) is followed by a programming event (032) and a mode event (021). Correlate them only if asset/session/time evidence supports the relationship. A command alone does not establish a changed process, and a shared IP alone does not establish an identity.

Service exceptions

Source outage: identify affected coverage, notify the service owner, record degraded visibility and restore through the approved process. Alert surge: group related signals and coordinate capacity; record temporary changes and expiry rather than silently suppressing critical coverage. Unreachable customer: follow the agreed escalation ladder, preserve evidence and document contact attempts.

Each shift: source health, open incidents and handover. Weekly during onboarding: readiness dependencies, customer explanations and alert workload.
